# OVELIO engineering instructions

Use this file for Codex, Claude Code and Google Antigravity. Claude Code imports it through [CLAUDE.md](CLAUDE.md). Antigravity loads it directly. [Antigravity workspace rules](https://antigravity.google/docs/rules/)

[docs/rebuild/TRACKER.md](docs/rebuild/TRACKER.md) records the current checkpoint, work in progress, lane ownership, migration ranges, platform contracts and release evidence. Start from the verified development checkpoint recorded there. Fetch the target branch and inspect any accessible worktrees before reimplementing missing work. [docs/parity/README.md](docs/parity/README.md) and [its backlog](docs/parity/backlog.md) retain the engine parity reference and research.

- Work by tracker or backlog ID. Keep implementation and named acceptance tests together. Use isolated worktrees for independent slices and coordinate shared contracts with the lead. Commit and push verified slices, record integration in the tracker and preserve rollback commits. Use fast-forward pushes and release gates before merging.
- Reuse Astryx, the OVELIO component kit, existing navigation and lane styles. Cover loading, empty, error and success states, keyboard interaction and 390 px layouts.
- Keep PostgreSQL migrations additive and in the owning lane's assigned range. Reuse the directory, event, job, mail, media and permission contracts. Check permissions in server queries before filtering, ranking, rendering or exporting rows. Mailbox access belongs to the active owner and explicitly granted active members. An admin role authorizes connection administration and carries the same content checks as other roles.
- Use engine source as a behavioural reference. Never copy from GPL Mautic or AGPL Listmonk. Keep Umami copyright in `NOTICE.md` if adapting its MIT-licensed code. Current engine pins are Mautic 7.2.2, Listmonk 6.2.0 and Umami 3.5.0. `sh scripts/fetch-refs.sh` fetches those versions into gitignored `.refs/` for reading. Cite engine file and line evidence when relying on engine behaviour. Check the exact version's licence and security before adding new dependencies or engine integration.
- Verify with `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` and the preview browser suite. CI also tests Compose integration, persistence, isolation and backup restoration. Use synthetic addresses and keep secrets outside Git. Record exact test results and any live-provider verification still pending.
- Treat Vercel as a developer preview. Use `/api/health` to confirm the exact deployed commit, mode and storage. Stage any public demo update with isolated sample data and verify it before promoting. Production uses Docker Compose with persistent PostgreSQL and media, worker and SMTP services, and the three engines.
- Update the README if a slice changes a user workflow or a known limitation. Update the tracker when handing off so the next agent can resume from repository evidence.
